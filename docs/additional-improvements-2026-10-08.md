# 新增改进项检查（2026-10-08）

检查基线：`codex/langchain-rebuild`，提交 `06a840c`。对照了已有的剩余工作、架构复查与下一步改进文档。本次未修改业务代码；新增以下五个有复现依据的问题。

## 1. P1：未再次检查的问题被标为“已解决”

位置：`src/repo_review_agent/pr_bot.py:84`；历史事务有同类逻辑，见 `supabase/migrations/20261006_atomic_history.sql:97`。

复现：在临时仓库放置 README 和含合成密钥样例的 `app.py`。先以 `max_files=100` 检查，再对完全未变的仓库以 `max_files=1` 检查。第二次只抽样 README，`files_skipped=1`；PR 比较却将 `Remove possible hard-coded secrets` 列入 `resolved_findings`，证据路径仍是 `app.py`。

原因：比较仅判断旧指纹是否在新结果中，不判断相关文件、检查器和检查范围是否覆盖。目录清单完整不等于文件内容检查完整。历史 SQL 同样仅以指纹缺席计算 resolved；该 SQL 判断来自代码检查，本次未连接数据库复现。

改进：记录各检查器的执行状态和实际覆盖范围；无法确认的问题进入“未复核”状态，只有相关范围完成复核或确认源文件已删除时才判定解决。

验收：同一仓库降低文件预算、关闭可选检查器、AI 失败时，不应凭发现缺席就宣告旧问题已解决；真正修复或删除目标仍可正常解决。

## 2. P2：Ruff 绕过主扫描器的排除范围

位置：`src/repo_review_agent/linters.py:31`、`:130`。

复现：临时仓库有正常 `app.py`、故意出错的 `fixtures/broken.py`，以及被受信配置 `ignore: ["vendor/**"]` 排除的 `vendor/ignored.py`。主扫描清单不含后两个文件，但启用 lint 后仍产生 `Fix 2 Ruff F821 lint finding(s)`，证据来自这两个排除路径。

原因：主扫描器的文件集合与忽略策略没有传给 Ruff，Ruff 使用自己的遍历规则检查整个 `.`。现有 `--isolated --no-fix` 能防止仓库配置触发修改，但没有统一检查范围。

改进：由扫描层向 Ruff 提供明确的允许文件集合，或统一应用排除策略；继续保留隔离配置和禁止修复。

验收：fixture 和配置排除目录不产生 lint 发现；允许范围内同样的违规仍可检出，源文件保持不变。

## 3. P2：常见 JavaScript 测试被误判为业务源码

位置：`src/repo_review_agent/scanner.py:226`。

复现：仓库仅含 `src/app.js` 和 `src/app.test.js`。扫描结果为 `test_files=[]`，两个文件均计入 source，报告错误提示 `Add automated tests for the core behavior`。

原因：文件名规则覆盖 `.test.ts/.tsx` 与 `.spec.ts/.tsx`，没有对应的 JavaScript 后缀。位于 `tests/` 或 `test/` 的文件能被目录规则识别，因此现有测试没有暴露源码旁放置测试的场景。

改进：补齐支持语言的测试命名约定，至少覆盖 JS/JSX 的 test/spec 后缀，同时保留对 fixture 的排除。

验收：源码旁的 JS/JSX 测试能被识别，普通业务模块不会被误算为测试；报告中的测试数量和缺少测试判断保持一致。

## 4. P2：切换项目后，较慢的旧响应覆盖当前项目详情

位置：`frontend/src/main.jsx:289`。

复现：使用真实 Chrome 和本地模拟 API，点击项目 A 后暂缓 A 的详情响应，再点击 B 并成功显示 B 的详情，最后放行 A 的响应。结果 B 的按钮仍为 active，但详情面板显示 `Evidence belongs to Project A`。

原因：`openProjectDetail` 的异步响应无条件写入共享详情状态，没有核对当前选择或取消先前请求。旧请求的 finally 也会修改当前加载状态。

改进：为项目详情请求增加取消能力及请求序号/项目身份校验；会话变化和反馈后的详情刷新也应使用一致保护。

验收：A 慢 B 快、A 快 B 慢，以及请求期间退出登录时，旧响应不能覆盖当前有效状态。

## 5. P2：认证缓存不会主动清理不再访问的过期 token

位置：`src/repo_review_agent/web.py:706`。

复现：构造 TTL 为 1 秒的缓存，在模拟时间 0 写入 1000 个不同的测试 token；在时间 100 写入一个新 token，缓存仍保留 1001 项。

原因：仅在 `get` 再次读到同一个过期 token 时才删除它；`set` 不清理旧项，也没有容量上限。正常刷新后旧 token 通常不会再次使用，长期运行会持续积累已过期条目。过期 token 不会因此继续通过验证，这是内存与数据保留问题。

改进：添加过期清扫和容量上限，确保并发访问受锁保护。

验收：持续产生新 token 后缓存大小有界；过期条目能在不被再次读取的情况下回收，未过期条目的验证缓存仍有效。
