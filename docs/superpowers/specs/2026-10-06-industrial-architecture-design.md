# 工程化架构改造设计（待确认）

日期：2026-10-06。

## 目标与约束

用户目标：再次检查整体正确性，并采用更适合工程化维护的架构管理项目。

设计假设：保留 LangChain、现有 CLI / HTTP / MCP / PR 入口、现有功能和单仓库部署；本轮以可靠性和可维护性为成功标准。没有证据要求独立服务的大规模部署，因此保持模块化单体，允许 API 和 worker 使用同一镜像、不同启动入口。

已验证问题见 `docs/architecture-correctness-audit.md`。本文件是可评审设计，尚未实施。

## 方案比较

| 方案 | 优点 | 代价 | 选择 |
| --- | --- | --- | --- |
| 局部修补现有文件 | 改动最少，能快速解决确定缺陷 | HTTP 与任务执行耦合、存储边界混乱仍在 | 作为第一阶段，而非最终结构 |
| 分层模块化单体 | 可独立测试领域和流程，维护现有部署，逐步迁移 | 需要显式接口、组合入口和兼容测试 | 推荐 |
| 分布式微服务与独立消息系统 | 便于服务分别扩容 | 增加网络故障、部署和一致性负担；当前无需求证据 | 暂不采用 |

## 模块边界

```text
repo_review_agent/
  domain/          # 发现、报告、反馈、评分、任务状态和领域错误
  application/     # 执行审查、回答报告问题、保存结果等用例与端口
  infrastructure/  # LangChain、Supabase、进程隔离、Git、OSV、遥测适配器
  interfaces/      # HTTP 路由与 DTO、CLI、MCP、PR 入口
  bootstrap.py     # 配置验证、适配器装配、资源生命周期
```

依赖规则：domain 不依赖其他层或供应商 SDK；application 依赖 domain 和自己定义的端口；infrastructure 实现端口；interfaces 通过 bootstrap 获得用例。只有 bootstrap 负责选择具体实现。端口用于现有可替换边界，不为每个函数增加接口。

`models.py`、`service.py` 等现有模块在迁移期间保留兼容导出。报告序列化从领域对象迁至专用序列化边界，消除 models/findings 依赖环。worker 使用应用用例，不导入 FastAPI 模块；CLI 的目标解析移到共享仓库适配器。

## 首批正确性修复

1. Ruff 执行强制只读；不受信配置不能启用修复。运行失败、超时和解析失败作为工具状态呈现，不伪装成通过。
2. 所有报告持久化字段经同一个安全投影生成，包括原始发现、AI、diff、Markdown。认证头不经过报告字段过滤。指纹与脱敏顺序确定且兼容已有反馈，避免重构悄悄更换发现身份。
3. 用领域错误区分输入、权限、找不到、容量、供应商和存储故障；入口统一翻译，存储正文不出现在公开响应。
4. 保留过滤前的脱敏发现，显式计算有效结果与策略应用记录。

## 用例与配置

- `ReviewOptions` 等输入对象属于应用层，避免 worker 使用 HTTP 请求对象。
- `ReviewExecutor` 编排获取仓库、扫描、规则、AI、策略、结果生成；LangChain 继续负责模型与工具执行，不承担数据库或 HTTP 路由职责。
- 使用显式配置对象，启动时校验模式、配额、时限和服务配置；入口创建实例后配置固定。测试可以构造两个互不污染的实例。
- 时钟、ID 生成、任务存储、历史存储、执行器作为可注入边界；业务代码不访问 Web 全局变量或存储适配器私有 `_request`。
- Web lifespan 启停 worker 和遥测资源；独立 worker 入口也有相同的显式生命周期。导入领域/用例模块不会创建应用、线程或连接。

## 历史保存与任务一致性

存储提供事务 RPC，并使用稳定的操作 ID。任务保存用 job ID，CLI 保存由应用在一次操作开始时生成 ID 并在重试中复用。相同 owner 和操作 ID 返回同一结果；相同 ID 携带不同载荷摘要时明确报冲突。

事务内完成：校验 owner 与操作 ID；锁定相应仓库；读取已提交的上次运行和反馈；计算/校验比较结果；写运行、发现、AI、策略信息；最后提交完成状态。RPC 仅服务角色可执行，查询仍保留 owner 隔离。

异步任务最终发布时校验当前 lease token、任务状态和租约有效期。最终历史写入与任务完成应在同一事务提交；禁止旧 worker 在失去租约或取消后发布结果。昂贵审查计算在事务外完成，避免长期锁。重试允许重复计算，持久化效果必须幂等，不承诺模型请求恰好执行一次。

同一仓库并发保存通过事务串行化确定比较基线。首次建立仓库也必须使用唯一键/原子 upsert，覆盖匿名 owner 的语义。迁移前检测旧数据冲突，遇到冲突停止并生成处理说明，不能自动删除历史。

## 策略信任边界

- 服务端策略是约束；第三方仓库不能通过自身文件禁用强制检查、忽略强制范围或降低最低严重度。
- 公开 HTTP 审查默认不信任仓库弱化规则。本地 CLI 提供显式受信模式，并在报告中显示策略来源。
- 报告保留原始发现、有效发现、抑制/降级原因、策略来源与版本。用户反馈和项目策略分别记录，不能混为一谈。
- ignore 会影响扫描前的证据范围，因此必须在扫描之前处理信任策略；不能只在结果阶段尝试恢复已忽略文件。

## 前端与项目管理

按 `review`、`history`、`feedback`、`questions`、`auth` 拆分前端功能，页面组合组件；请求生命周期与任务恢复放入专用 hooks；共享 API 客户端统一错误与取消语义。保留当前界面和交互，逐个迁移并运行既有浏览器流程。

开发入口统一提供 lint、后端测试、前端测试、构建和数据库集成测试。新增依赖方向检查，将跨层反向导入和循环依赖纳入 CI。为新增应用边界加入类型检查，逐步覆盖旧模块；用短 ADR 记录事务语义、策略信任和兼容决定。部署依赖生成可复现锁定文件，并由 CI 检查与声明一致；包的可安装版本范围单独维护。

## 迁移与验收

顺序：先把审计问题变成失败回归并修复，再提取应用输入/执行用例和组合入口，然后改事务存储与策略信任，最后拆前端并加架构检查。每一步保留外部接口兼容测试，禁止把全部模块一次搬完后才验证。

数据库变更先添加表/列/RPC，在隔离 PostgreSQL 中验证旧迁移链和新迁移；部署先迁移后切换新适配器。回退到兼容版本时保留新数据，不删除列。新原子保存模式缺少迁移时应明确报告不可用，不静默退回多次非原子写入。

验收必须覆盖：

- 当前后端、前端与六个浏览器流程继续通过。
- 真实 Ruff 配置开启自动修复时源码字节不变且违规可见。
- 存储载荷/错误响应的合成敏感值不泄漏。
- 真实 PostgreSQL 中注入中途失败不留下部分运行；双 worker 竞争、重复提交、响应丢失后重试、取消与租约过期后提交均满足约束。
- 并发首次保存不重复创建仓库；反馈和比较读取有一致基线。
- 不受信仓库无法弱化服务端策略，受信模式行为显式且原始发现可查。
- 应用层可在不导入 Web 的情况下运行；两应用实例配置隔离；关闭服务不遗留工作进程。
- CI 阻止新的反向依赖；迁移前后 HTTP/CLI/MCP/报告兼容用例通过。

真实外部模型、Langfuse 和 GitHub 写入单列为集成验证，缺少配置时明确报告未验证。数据库事务测试不能用 HTTP Mock 测试代替。本设计确认后，再按这些边界编写逐步实施计划。
