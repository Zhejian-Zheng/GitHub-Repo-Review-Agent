## 已复现：1. 分析工具截断 JSON，可能丢掉全部 findings

优先级：高。位置：`src/repo_review_agent/review_tools.py:195`，尤其第 201、213 行。

`analyze_repository` 把完整 metrics 放在 findings 前面，随后对序列化后的 JSON 直接截取 6000 字符。metrics 内含 `review_coverage.inventory_paths`，会随仓库文件数增长。

本地临时仓库探针：创建 200 个 `src/component_000_with_a_reasonably_descriptive_name.py` 形式的文件，内容为 `value = 1`，再调用 ReviewSession 的真实分析工具。结果：

- 工具返回长度恰好 6000；`json.loads` 失败。
- 输出不包含 `"findings"` 键。
- 完整 report 实际包含 6 个规则发现。

因此缺失发生在提供给模型的工具观察中，而非底层扫描没有发现问题；最终报告仍可能有规则发现，但模型做总结、定位和后续取证时拿不到这一轮完整结果。

建议：为模型构造专用摘要，只保留计数、覆盖状态和优先发现；文件清单经现有 list_files 分页获取。先按字段、条目控制大小，再序列化，提供明确的截断标记和后续读取入口。

验收：200/500 个长路径文件下输出仍是合法 JSON；关键发现始终可见；限制信息完整且可续读。

## 已复现：2. 中文追问遗漏相关证据

优先级：中。位置：`src/repo_review_agent/questions.py:67`。

候选排序使用 `re.findall(r'\w+', question.lower())`，然后按完整词是否出现在 title/evidence/recommendation 中打分，最后只保留 8 个。连续中文连同其中的英文字母可能成为一个完整字符串，与英文标题不匹配；全部零分时沿用报告原始顺序。

探针：报告前 8 项均为日志问题，第 9 项是 `SQL injection`，证据位于 `database.py`。英文提问 `How do I fix SQL injection?` 能选中 database.py；中文 `如何修复SQL注入问题？` 不能。无需调用模型即可稳定复现。这发生在所有 provider 共用的证据选择阶段，换模型无法找回已经被剔除的材料。

建议：先支持中英文混合切分、英文标识符和文件路径匹配，纳入类别和稳定规则 ID；零相关命中时应明确表示检索不足，避免任取前 8 项。是否引入语义检索应由真实问答样例评测决定。

验收：同义中英文问题都能取到第 9 项证据；对完全无关问题不输出貌似相关的引用。

## 已复现：3. 全局覆盖标记令大仓库的已修复问题长期未复核

优先级：中，属于保守策略的可用性限制。位置：`src/repo_review_agent/analyzer.py:131`、`src/repo_review_agent/resolution.py:43`。

规则复核使用一个全局 `rules_complete`。文件超过 250 个、某个读取不完整或 Dockerfile 超过 3 个等条件，会阻止其他无关规则确认解决。

探针：临时仓库含一个 app.py 和 250 个非空 Markdown 文件，第一次产生缺少许可证的发现；加入 LICENSE 再次扫描，文件共 252 个，许可证发现已消失，但 `rules_complete=False`、`finding_rechecked=False`。即使增加 max_files，也不会绕过独立的 250 文件条件。

建议：保持失败时保守的原则，记录每个检查器实际验证的范围与状态。许可证存在性只需许可证检查完成即可确认，不应依赖所有源文件秘密扫描都完成。Python 和 SQL 的决策应继续用同一组回归案例校验。

验收：大仓库补齐 LICENSE 后该发现可以解决；被跳过的源文件风险、禁用检查、策略改变和 AI 未提及仍保持未复核。

## 提升方向：4. 从规则回归提升到真实缺陷质量验证

优先级：高，产品效果的主要验证缺口。

当前 `tests/fixtures/evaluation/dataset.json` 只有 healthy-python-service 和 risky-js-app 两个样例。它们已有 acceptable_findings 标签，CI 设置了 precision 门槛，比前轮有所提升；但 CI 没有指定 provider，默认 `none`，当前评测结果仍只验证确定性规则标题。

`evaluation.py` 已支持缺陷位置标签，但明确将 semantic_precision/semantic_recall 保留为 null；位置吻合不能证明缺陷解释正确。不能把本次规则 precision=1 解释为 AI 的真实准确率。

建议先构建一批人工判定的缺陷／修复前后成对样例，覆盖跨文件调用、授权边界、异常分支、竞态、提示注入和无缺陷反例。将无外部调用的 CI 回归与受控的真实模型评测分开，记录模型、提示词版本、重复次数和人工判断。用误报率、缺陷召回和建议采用率指导后续功能开发。

## 提升方向：5. 增量审查补上调用方和依赖上下文

位置：`src/repo_review_agent/review_tools.py:70`、`src/repo_review_agent/incremental.py`。

当前 changed_files 能优先扫描变更文件，模型也可以主动使用搜索工具，但没有自动构建 import/call 关系。仅修改公共函数时，漏掉调用方的风险仍依赖模型主动发现。

建议先支持 Python 或 JS/TS 中一种语言，以预算限制的一跳依赖补充调用方、被调用模块及相关测试；报告应展示哪些变更文件和关联文件已检查，哪些受预算影响未检查。不要直接扩展成无界全仓调用图。

验收：针对“函数签名改变但调用方未更新”等跨文件成对样例，比较提升前后的检出率与 token 消耗。

## 提升方向：6. 漏洞报告从 advisory ID 走向可执行修复

位置：`src/repo_review_agent/vulnerabilities.py:124`、第 174 行附近。

当前只解析 npm package-lock v2/v3 和精确 requirements 版本，批量查询结果生成统一 medium 的发现，并明确提示严重度未知。uv.lock、pnpm-lock 等尚未覆盖；修复建议没有准确 fixed range。这是明确的功能范围，不能把不支持解读为无漏洞。

建议先补与本项目实际使用相关的 uv.lock，再增加有缓存和请求上限的 advisory 详情查询；分别展示权威严重度、受影响范围、修复版本及未知项。继续把“版本存在修复”与“升级通过兼容性验证”区分开。
