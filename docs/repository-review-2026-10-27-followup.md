## 1. Ruff 数量变化导致错误的“已解决”记录

位置：`src/repo_review_agent/linters.py:104`；相关逻辑在 `findings.py:14`、`resolution.py:42` 和 `pr_bot.py:48`。

**复现**：创建仅含 `print(missing_a)` 的 `app.py`，开启 Ruff 分析；随后保留原行，增加 `print(missing_b)`，再次分析并调用 `build_pr_review_diff`。

实测差异输出：

```text
before:   Fix 1 Ruff F821 lint finding(s)
after:    Fix 2 Ruff F821 lint finding(s)
resolved: Fix 1 Ruff F821 lint finding(s)
new:      Fix 2 Ruff F821 lint finding(s)
```

`missing_a` 并未修复。原因是数量进入标题，标题又参与 fingerprint；样本路径列表也参与 fingerprint。当前扫描完整时，旧 fingerprint 消失即被视为已经解决。问题身份随展示信息变化，破坏 PR 差异统计，并影响同样依赖 fingerprint 的历史记录和反馈关联。本轮实测的是本地 PR 差异，未向 Supabase 写入验证数据。

**修复方案**：

- 保持当前“同一 Ruff 规则汇总为一条发现”的语义，为该规则组生成有版本的稳定 fingerprint，依据规则代码和来源；数量、展示标题、抽样路径不参与身份计算。
- 增加明确的 `rule_id`，例如 `ruff.F821`。仅添加 `rule_id` 不够，必须同时调整 fingerprint 的计算分支。
- 按规则组判断生命周期：当前仍有 F821 就更新原组；只有完整执行 Ruff 且该组没有诊断时才标为已解决。部分扫描继续保留“未复核”。
- 明确旧 fingerprint 的兼容处理。不能可靠匹配的旧记录保留为未复核；不要仅因身份算法升级就把它们标成已解决或扩大旧反馈的作用范围。同步核对 Python 与 Supabase 的复核判定。

**验收**：1→2、2→1 条同规则诊断及样本路径变化均不产生虚假的解决记录；2→0 且完整扫描才解决；未执行或未完整执行 Ruff 时不宣称修复；历史反馈的迁移有明确测试。

## 2. 初始 AI 提示词直接切断 JSON，可能丢失整个问题列表

位置：`src/repo_review_agent/llm.py:158`。直接模型调用和 Agent 的初始提示词都使用 `build_review_prompt`。

实测报告含 6 条发现，但数据区被裁成 24,000 字符，无法被 `json.loads` 解析，且连 `"findings"` 键都没有。较大的 `metrics.top_level_items` 位于发现之前，耗尽字符额度。上一轮对分析工具返回值的分页修复没有覆盖此处。静态报告本身仍有发现；受损的是送往模型的初始上下文，本轮未调用真实模型来评估具体输出。

**修复方案**：

**验收**：长文件名、大目录、长证据和增量扫描输入下，数据区均为合法 JSON、符合预算，关键发现不会被目录列表挤掉；直接调用和 Agent 两条路径都有回归覆盖。

## 3. 多文件证据被错误归到第一个文件

位置：`src/repo_review_agent/questions.py:97` 和 `:112`。

**复现**：`package.json` 含依赖 `beta: "*"`，`requirements.txt` 含未限定版本的 `alpha`。生成报告后，以无需模型的模式询问 `Why is alpha in requirements.txt unconstrained?`。

返回引用的 `path` 是 `package.json`，但 evidence 同时包含：

```text
package.json: dependencies.beta uses floating version '*'
requirements.txt: alpha is unconstrained
```

原因是 `_evidence` 取 `evidence_paths[0]` 作为整组证据的唯一位置。前端据此显示错误的文件标题，模型也会收到被错误归属的证据对象。

**修复方案**：

- 从规则产出端保留证据与路径的对应关系，追问检索按文件拆分候选证据。
- 兼容旧报告：无法可靠拆分的证据保留全部关联路径，并明确为多文件证据；不能把同一整段证据简单复制到每个路径下。
- 同步调整回答引用结构与前端展示；没有可靠行号时不生成行号。

**验收**：分别询问两个依赖时，引用各自的清单；汇总提问保留两处来源；旧报告、多路径和无行号证据均不会冒充单文件精确引用。

## 4. 切换报告后，旧报告的异步回答仍会显示

位置：`frontend/src/features/Questions.jsx:10`；关联挂载位置 `frontend/src/main.jsx:284`，报告替换逻辑 `frontend/src/hooks/useReviewJob.js:222`。

**复现**：通过模拟接口完成 `old-project-only` 的评审，提交追问并延迟接口返回；在等待期间点击 Demo 替换报告，再释放旧回答。Chrome 浏览器实测：页面已经没有旧项目标题，但 Demo 下出现 `OLD PROJECT ANSWER ONLY`。

原因是同一位置的 `ReportQuestionForm` 在报告替换时保留组件状态，且异步返回没有校验报告身份。已完成的回答也不会随报告替换自动清空。现有正常提交追问的测试没有覆盖这一场景。

**修复方案**：

- 每次安装或替换报告时生成新的报告实例标识，传给追问组件并用作 React `key`；不能只用仓库名，因为同一仓库也有多次评审。
- 报告更换时清空问题、回答、错误和等待状态。对在途请求使用 AbortController，并把 signal 传至会话刷新和请求层。
- 回调写状态前校验当前报告实例与请求序号；即使取消没有阻止响应到达，也不能让旧响应覆盖新报告。

**验收**：旧请求延迟成功、延迟失败，以及回答已完成后三种情况下切换 Demo，都不携带旧回答或错误；关闭报告、退出登录和重新评审同样使旧请求失效。
